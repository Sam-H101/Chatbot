# Document Chatbot (PoC)

A small standalone chatbot that answers questions with the Claude API, using your own API key. You upload documents, Claude pulls metadata out of each one (title, type, summary, keywords), and everything goes into an embedded SQLite database with full-text search. When you ask a question, the app finds the most relevant passages and sends them along with it.

## Run it

By default the app runs on local models through [Ollama](https://ollama.com), on your own NVIDIA GPU: no API key, and documents never leave the machine. The defaults are sized for an 11 GB card (GTX 1080 Ti):

- `qwen3.5:9b` (about 6.6 GB) answers questions and extracts metadata.
- `minicpm-v4.6` (about 1.6 GB) reads scanned PDF pages. Pages that have embedded text skip the model.
- `qwen3-embedding:0.6b` (about 640 MB) turns passages and questions into vectors, so questions are also searched by meaning. Without it, search is by keywords only.

Containers need the NVIDIA Container Toolkit to use the GPU (one-time setup, inside WSL on Windows). See NVIDIA's install guide, then run `sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker`.

```bash
docker compose up --build -d
docker compose exec ollama ollama pull qwen3.5:9b
docker compose exec ollama ollama pull minicpm-v4.6
docker compose exec ollama ollama pull qwen3-embedding:0.6b
```

Open http://localhost:8000 and upload some files.

To use the Claude API instead, run `LLM_BACKEND=claude docker compose up --build` and paste your Claude API key into the page. The rest of this README describes both backends. Token and caching notes apply to Claude.

The key stays in your browser's localStorage and goes along with each request. The server never stores it. If you'd rather set it on the server, export `ANTHROPIC_API_KEY` before running `docker compose up`.

Anyone who can reach the port can use the app. To ask for a password, put `APP_PASSWORD='<your password>'` in a `.env` file beside `docker-compose.yml` (git ignores it) and run `docker compose up -d` again; see **Login** below. Keep the single quotes: without them compose reads a `$` as the start of a variable and ` #` as the start of a comment, so `$ecret1` would become an empty password (no login at all) and `pa$word` would become `pa`. The log says at start whether a login is on (`docker compose logs chatbot`).

The database is a single file, `/data/metabase.db`, kept in the `metabase` Docker volume. No database server is needed. The original uploaded files are kept beside it, in `/data/files`. Uploads are read in the background by one worker thread, which is why gunicorn runs a single worker process (see the Dockerfile). The thread starts with the app (`app/gunicorn_conf.py`), and its queue lives in the database. `docker compose up` also starts a `backup` service that backs up both every night (see **Backups**). On Windows, where Docker runs inside WSL, see **Reach it from the LAN** for keeping port 8000 open to other machines across restarts.

## What it does

| Feature | How |
|---|---|
| Upload | PDF (text or scanned), DOCX, and any UTF-8 text file (txt, md, csv, json, code…). The upload only sends and stores the file (with a progress bar while it travels); reading happens in the background, see the next row. A file that can never be read (a PDF that doesn't open, a damaged DOCX, a file that isn't UTF-8 text, or one with no text at all) gets a 400 at once and is not queued or kept |
| Background reading | Each upload becomes a job in the `jobs` table, and one worker thread reads the jobs in order. The upload list shows each job live: its stage ("Reading page 40 of 312", "Analyzing with …", "Indexing for search by meaning: 64 of 120 passages") and a progress bar, then **Added · model** (or the reason Auto switched to Claude). A queued job waits still; only the one being read moves. On a phone, where the list is in the closed drawer, the ☰ button counts the jobs under way and turns red when one waits for you (failed, or a cost to confirm). Jobs survive a page reload: the list comes back from `GET /api/jobs`. A running job can be cancelled: a call to a local model it waits on is cut off at once (Ollama stops working on it, and the next job starts), and otherwise it stops after its current page or Claude call. A failed job shows its error with **Retry**; pages a model already read are kept with the job, so a retry, or a job cut off by a restart, carries on where it stopped and doesn't pay for those pages twice. Jobs left running by a restart are queued again as soon as the app is back up, with no need to open the page. API: `POST /api/upload` answers 202 `{job}`; `GET /api/jobs`, `GET /api/jobs/<id>`, `POST /api/jobs/<id>/cancel`, `/retry` and `/confirm` |
| PDF reading | Every reader returns one text per page, and a document's text keeps its pages apart with a form feed (`\f`), so every chunk records the pages it spans (`page_start`, `page_end`) for citations; search and analysis treat it as a paragraph break. Other files have no pages: a form feed in a text file is stored as a line break. Local models: pages with a text layer are taken as they are, and the vision model (`OLLAMA_VISION_MODEL`) reads only scanned pages. Claude: by default (`CLAUDE_PDF_PAGES=scanned`) the same: only scanned pages go to Claude, as a new PDF of just those pages, with their page numbers in the prompt. The **Claude reads every page** box beside "Read with" (shown for Claude models) has Claude read every page as text and image instead, which is worth its cost for complex tables and layouts. Claude reads `PDF_PAGES_PER_CALL`-page pieces in parallel. A page counts as scanned when its text layer has fewer than `MIN_PAGE_CHARS` visible characters |
| Cost estimate | Before a job reads with Claude, it estimates the cost: pages, pages Claude reads, about 2,000 input and 600 output tokens per page Claude reads, plus the analysis (about 4 characters a token; a text longer than `CLAUDE_ANALYZE_CHARS` adds one call per section, counted as the analysis will split it, pages kept whole, about 1,000 output tokens of notes each, and one combining them), priced with `PRICES` in `app/llm.py`. A Claude model missing from `PRICES` is estimated at the dearest price listed there, and the row says so. The upload row shows the estimate. At `CONFIRM_COST_USD` (default $1.00) or more, the job waits for **Start** or **Cancel**. **Start** covers the amount shown: a retry that would cost more asks again. Auto only estimates Claude when it actually switches to it, and when only the local analysis failed, the estimate covers just Claude's analysis of the text read locally |
| Re-read | In the **Table** view, tick documents and pick **Re-read with** (any model, with the same every-page box for Claude): their kept originals are read again and each document's text, metadata and model are replaced in place, keeping its id and upload date. If the new analysis fails (a refusal, an API still overloaded after its retries, a local reply that isn't JSON), the re-read fails and the document keeps everything it had; **Retry** redoes only the analysis, since the pages read are kept. Documents uploaded before originals were kept can't be re-read. API: `POST /api/documents/<id>/reread` with `{"model": "…", "claude_pages": "scanned" \| "all"}` |
| Analyze | Structured JSON output: title, doc type, summary, keywords. A document that fits one call (`CLAUDE_ANALYZE_CHARS` for Claude, `OLLAMA_ANALYZE_CHARS` for a local model, kept within `OLLAMA_NUM_CTX`) takes one call. A longer one is analyzed section by section (`app/sections.py`): it is split into sections of about equal size at page breaks, or else at paragraphs, each within that limit; the same model takes notes on each section (key topics, specifications and values, procedures, warnings), and a last call turns the notes into the metadata, so the whole document counts, not just its start. For a local model, sections are sized by an estimate of their tokens, with a token for every digit as qwen3.5 counts them (tables of figures run at about 1.3 characters a token, prose at 4), and Ollama is asked to refuse a prompt too long for its context rather than silently drop its start (a reply that ran past the end of the context is caught too); text that is still too dense is read again in smaller pieces. Analysis calls start the local model with the same settings as questions, so Ollama doesn't load it again between an upload's analysis and a question. When the notes are too long for one local call, neighbouring notes are merged first; a merge whose reply can't be used leaves its notes as they were and merges fewer at a time. The upload list shows each step ("Analyzing section 3 of 12 with …", "(sampled from 61)" when sampling, "Combining the notes of 12 sections"), every call is in the usage log, and each section's notes are kept with the job, so a retry doesn't ask for them again. At most `ANALYZE_MAX_SECTIONS` (default 24) sections are read: a document needing more is sampled evenly from first to last section, and marked `partial: 24 of 61 sections, 39% of the text` (shown on the library card). A section whose reply can't be used (not JSON, cut off, a refusal) is left out and counted the same way. File names are cut to 200 characters in the prompts. If the analysis fails, a new upload is still added and searchable, marked `none: <reason>`; a re-read, or an upload replacing its duplicates, fails instead, so no metadata is lost. Documents analyzed before this was added and marked just `partial` were analyzed from their start only; a re-read covers them whole |
| Metadata base | SQLite tables `documents` and `chunks` (with each chunk's pages), plus FTS5 indexes over the metadata and the full text (porter stemming), `chunk_vectors` (one float32 embedding per chunk, with the model that made it), `conversations` and `messages` (saved chats), and `jobs`, `usage` and `instructions`. Older databases gain new columns and tables automatically when the app starts; their documents keep working without a kept file, hash, page numbers, vectors or unit check |
| Originals | Every uploaded file is kept in `FILES_DIR` (default `/data/files`), stored once per distinct content and named by its SHA-256. **Open** in the library and in the table view shows it: PDFs open in the browser's viewer and plain text as text; other types download. `GET /api/documents/<id>/file` serves it. Deleting a document removes its file once no other document uses it. Documents uploaded before originals were kept have no file and no Open link |
| Duplicates | Uploads are hashed (SHA-256). If the same file is already in the library, the upload stops before any model reads it, and its row in the upload queue asks: **Replace** (read the new upload, then delete the earlier copies), **Keep both**, or **Skip**. Through the API: the form field `on_duplicate` is `replace` or `keep`; without it the answer is 409 with the earlier copy's id, file name, date and model. A copy that is still queued or being read also counts (say the file was picked twice): the 409 then has `in_progress: true`, and only **Keep both** or **Skip** are offered. Documents uploaded before hashing never count as duplicates |
| Usage | Every model call (reading PDF pages, analyzing a document, each section of a long one included, embedding passages and questions for search by meaning, answering) is logged with its model, tokens and cost in the `usage` table as it happens, including calls made by uploads that then failed, Claude answers that ended in a refusal, and answers stopped or broken off part way (their output tokens estimated, see Streaming answers). Calls made by a job carry its `job_id` and are linked to the document when the job finishes (failed attempts before a successful retry too). Deleting a document keeps its rows but clears their `doc_id`, because SQLite reuses ids. The **Usage** button shows totals per model and per day for the last 7, 30, 90 or 365 days; `GET /api/usage?days=30` returns the same. Claude costs come from the list prices in `PRICES` in `app/llm.py` and are estimates, not the invoice. Cache reads have their own price per model (5% of the input price on Opus and Sonnet 5.5, 2.5% on Fable 5.2, 10% on Haiku 5.5), and cache writes cost 1.25x the input price. Models missing from the table count as $0. Local models cost nothing. If the log can't be written (say the database stays locked), the answer or upload still goes through and the error goes to the server log |
| Search | The sidebar search box matches documents by metadata and lists passages that contain the words, with highlighted snippets and, for PDFs, their page. It searches by keywords only, since it marks the words it found. Common words ("the", "will", "it") are left out when other words remain; typed alone they are searched for, so "will", "IT" or "WHO" still find a will, an IT policy or WHO guidelines |
| Chat | Each question is searched by keywords and by meaning (next row) for the top `TOP_K` (5) passages, which go into the prompt. Each passage is labelled with its file and, for a PDF, its page or pages, with a `[Page n]` line where a new page starts inside it, and the model is asked to cite like (Tractor Manual.pdf, p. 3), the example made from the first passage that has a page. It is asked for pages only when an excerpt has one: asked in general, `qwen3.5:9b` gave page-less excerpts a made-up page in 7 of 15 answers. The prompts name no example file of their own: with "Chapter 7 Brake.pdf" as the example, `qwen3.5:9b` cited that file, which wasn't in the library, in 4 of 24 answers about brakes. Below each answer, a chip per source document shows its file and pages ("Tractor Manual.pdf, pp. 1-3"); clicking it shows the passages the answer was given, as the model read them (misprints corrected), how each was found, and **Open page 1**, which opens the kept PDF at that page; each `[Page n]` line in a passage opens page n. Documents read before pages were kept (the library from before this) are cited by file name only. A question that finds no passage in any document ("Summarise everything in my library", or small talk) is given the documents' titles and summaries instead (newest first, up to 6,000 characters), and the answer says so. When none of this has the answer, the model says so; for a figure or specification (a capacity, pressure, torque, clearance, …) it stops there rather than give a typical or estimated value, and other questions it may answer from general knowledge, saying that it does. (Told just to fall back on general knowledge, `qwen3.5:9b` gave the library's tractor a "typical" hydraulic oil capacity of 11.0 litres; asked of a chapter without tire pressures, it gave general-knowledge pressures in 2 of 3 answers before, 0 of 3 now.) Answers are shown as plain text, as the model writes them: Markdown such as `**bold**` is not rendered. A question can be 20,000 characters long at most (each one is kept, and sent again with every later question of its conversation); the page says so before sending a longer one, and keeps it in the box. API: `POST /api/chat` with `{"question", "model", "doc_ids", "conversation_id"}` returns the whole answer at once (`answer`, `usage`, `model_label`, `switched`, `conversation_id`, `title`), `sources` (`[{doc_id, filename, title, pages, excerpts, has_file, pdf}]`, `excerpts` being indexes into `excerpts`), `excerpts` (`[{doc_id, filename, idx, page_start, page_end, match, text, …}]`) and `overview` (true when it was given the titles and summaries); the page uses the streamed route in the next row |
| Streaming answers | The page shows an answer as the model writes it, with a caret at its end, and a **Stop** button in place of **Ask** while it is written. `POST /api/chat/stream` takes the same body as `/api/chat` and answers with Server-Sent Events (`text/event-stream`, one JSON `data` line each), read through `fetch` as they arrive: `start` at once (`conversation_id`, `title`, `answer_id`), `meta` once the model has begun (`conversation_id`, `title`, `model`, `model_label`, `switched`, `sources`, `excerpts`, `overview`, `scope`, `left_out`), then `delta` (the next piece of text, a JSON string), then `done` (`answer`, `status`, `usage`, `conversation_id`, `title`, `turns`) or `error` (`{error, status, kept, conversation_id, title}`). The headers are `Cache-Control: no-cache` and `X-Accel-Buffering: no`, and a comment line goes first, so nothing on the way holds the answer back. A request that is wrong (empty question, a question over 20,000 characters, unknown model, deleted conversation, a Claude model with no key) gets a plain HTTP error, as from `/api/chat`. Claude streams with the same request as before (so the prompt cache is shared); Ollama's `/api/chat` with `stream: true`. **Stop** aborts the fetch and tells the server how much of the answer the page showed (`POST /api/chat/stop` with `{conversation_id, answer_id, shown}`, `shown` in characters); so does leaving or reloading the page mid-answer. The server ends the answer before its next piece (or as soon as the model begins, if it hadn't), closes the model's stream (on staging, Ollama's log showed the generation cancelled at once) and keeps exactly what the page showed, marked "Stopped": the server alone notices a closed stream only when a piece fails to go out, and the piece or two sent just before were never shown. Stopped before its first words, the question is kept with no answer, and the page says "Stopped before the answer began" then and after a reload. If the model fails after it began writing, the answer ends there: the error event has `kept: true`, the page keeps the words with the reason, and the answer is saved as broken. A Claude refusal after some words (no fallback model took over) drops them (`kept: false`). An unexpected server error says only that the answer failed; its details stay in the server log. Without streaming (a browser that can't read a response as it arrives, or a server without the route), the page asks `/api/chat` instead. Every call, stopped ones too, is in the usage log; Ollama counts tokens only at the end and Claude counts output only at the end, so a stopped or broken answer's output tokens (and Ollama's input tokens) are estimated |
| Saved conversations | Every question and its answer are kept on the server (`conversations` and `messages` tables), with what the model was sent: the question with its excerpts, which later questions send back as history, byte for byte, so Claude's prompt cache still hits. The server reads a conversation's history from there rather than trusting the page. A question is kept as soon as it is asked, its answer marked as being written until it ends: a page reloaded meanwhile, or another tab, shows the question with "Still being answered" and reads the conversation again until the answer is in. A question whose answer failed is kept with the reason. Answers without text (stopped before their first words, failed, still being written) are left out of the history later questions send. A restart marks answers it cut off as failed ("The server restarted before this was answered"). A deleted conversation's id is never given to another, so a tab or phone that still has it open gets "This conversation was deleted" rather than writing into someone else's new chat. **Chats** (header) lists them, the one asked last first: a column beside the chat on screens 1280 px and wider (Chats shows or hides it, and the page remembers), and a drawer below that and on phones, where **New chat** sits at the top of the drawer. Click one to see it again, with its answers' sources, notes and tokens; ✎ renames it (Enter saves, Escape keeps the old title) and ✕ twice deletes it (its model calls stay in the usage log). A new chat's first question gives it its title (cut at 80 characters). The page remembers the open conversation, so a reload comes back to it. Each conversation keeps the model choice and the documents its last question was limited to: picking it from the list brings both back (deleted documents are taken out of it, also while a question is answered; if all of them were, the chip says **Chosen document deleted**; a document replaced by a new upload with **Replace** stays chosen as its new copy). **New chat** starts on all documents. An answer whose document has since been deleted, or whose id a later upload was given, keeps its passages but no longer links to the file. History in the browser from before this is not carried over. API: `GET /api/conversations` (`id`, `title`, `created_at`, `updated_at`, `model`, `doc_ids`, `questions`), `GET /api/conversations/<id>` (with `messages`: each question, and each answer with `sources`, `excerpts`, `model_label`, `usage`, `status` of `answering`, `done`, `stopped`, `broken` or `failed`, and `error`), `PATCH /api/conversations/<id>` with `{"title": "…"}` (200 characters at most), `DELETE /api/conversations/<id>`. `/api/chat` and `/api/chat/stream` take `conversation_id`; without it they start a new conversation, and an API client may still send its own `history` (the `turns` earlier answers returned), which is used for that answer. A failed `/api/chat` names the conversation its question was kept in (`conversation_id`, `title`) beside `error` |
| Search by meaning | Every passage gets an embedding from a small local model (`OLLAMA_EMBED_MODEL`, `qwen3-embedding:0.6b`, 1,024 dimensions), made in the upload job after the text is chunked. A question is embedded too (with an instruction, as qwen3-embedding expects), compared with all passages (cosine, with numpy over vectors kept in memory and reloaded when uploads, re-reads or deletes change them), and the nearest are blended with the keyword search (FTS5) by reciprocal rank fusion. So "hydraulic oil capacity" also finds a passage that only says "transmission fluid … 38.0 litres". Asked of all documents, a passage found by meaning alone must be no less similar than `SEARCH_MIN_SIMILARITY` (0.47), so greetings, thanks and other small talk get no passages (on the live library they came to 0.45 at most), and within `SEARCH_MEANING_MARGIN` of the nearest, so loosely related passages don't fill the places (and the source chips) of a question with a clear answer. Scraps of a longer document under 100 characters (the tail of a table, a page footer) are left out of search by meaning, as they carry next to no meaning and came nearest to almost any short question; keywords still find them, and a document's only chunk counts however short. Common words ("what", "is", "the") and greetings ("hi", "thanks") are left out of a question's keyword search, so they no longer make every passage a keyword match. Small talk that shares other words with the documents ("good morning") still gets the passages that have them. Documents without vectors (the library from before this, or uploads made while the model was unavailable) are embedded by the job worker when it has no job to do, from their stored text, with no model reading them again. If Ollama or the embedding model is unavailable, uploads go on without vectors and questions are searched by keywords only. A batch of passages that fails (say more than one call can embed in 60 seconds, as tables can on a slow machine) is sent a passage per call; a passage that fails even alone is set aside for 30 minutes, so it can't hold up the rest of the library, and embedding passages pauses for two minutes. A question whose embedding fails is searched by keywords only for two minutes; the two pauses are separate, and the **Ask** dialog says when one is on. The embedding model is small and its ranking is rough: a passage that answers a question can rank below loosely related ones, and stay out of the top `TOP_K`. Embedding calls are in the usage log (`embed`, `embed-query`) at $0. `GET /api/search/status` gives the model, passages and how many are embedded |
| Ask chosen documents | The **Ask** chip under the question box shows **All documents** or the documents questions are limited to; clicking it opens a list to filter and tick, and its ✕ goes back to all. **Ask** on a library card or a table row limits questions to that document, and **Ask about N** in the table view to the selected ones. Both searches then look only in those documents, the model is told which they are, and each question shows "Only in …". The question is taken to be about them, whatever it says: their nearest passages count however far they are in meaning, and when fewer than `TOP_K` are found (no vectors yet), their opening passages make up the rest, so "What is this document about?" or "Summarise it" has the document to work from. The choice is kept in the browser; deleted documents drop out of it, but when all of them are deleted, the chip says **Chosen document deleted** and questions wait for a new choice (or ✕) rather than quietly asking every document. A chosen document replaced by a new upload (**Replace**) stays chosen as its new copy. The documents are also kept with each conversation, so picking a saved conversation brings its choice back, and **New chat** goes back to all documents (so a new conversation isn't quietly limited to the documents of the one picked before). API: `POST /api/chat` with `"doc_ids": [1, 2]` (`[]` or none means every document; ids that no longer exist are left out, and 400 if none is left) |
| Model pickers | "Read with" (in the upload box) picks the model that reads and analyzes uploads; "Answer with" (under the question box) picks the chat model. Each offers **Auto**, every model pulled into Ollama that can chat (an embedding model, such as `OLLAMA_EMBED_MODEL`, is left out: Ollama's `/api/show` doesn't list "completion" for it), and the Claude models. The page remembers both choices, a saved conversation brings back the model its last question used, and every answer and upload shows which model did the work |
| Auto | Uses the local model (`OLLAMA_MODEL`) and switches to Claude (`CLAUDE_MODEL`) when Ollama is down, errors or gives no answer within `OLLAMA_TIMEOUT`, or when a chat prompt is too long for `OLLAMA_NUM_CTX` (estimated with a token for every digit, as for analysis). It only switches when a Claude key is available (browser or server), and says why it switched. A streamed answer switches when Ollama fails before its first words; once it has begun, a failure ends the answer there instead of starting again on Claude. A long conversation doesn't count as too long: once its history outgrows the local context (each earlier question is sent again with its excerpts, so about 7 questions with the default 16K), the local model is given the latest exchanges that fit, and the answer says how many earlier questions it wasn't given. Only a question too long for the local model on its own goes to Claude, which is always given the whole conversation. For an upload, Claude reads the file only if the local reading failed; if just the local analysis failed, Claude analyzes the text the local models already read |
| Instructions | The **Instructions** button holds rules added to the system prompt of every question, for local models and Claude alike (for example how to handle units). Each can be switched on or off, and they are stored in the database, so they apply to everyone using the app |
| Unit checks | Before passages go to the model, litre and gallon figures printed side by side are checked against each other (`app/units.py`). If they disagree, the litre figure is trusted and the gallon figure is recalculated; a quarts-printed-as-gallons misprint is shown as quarts. The stored document text is not changed. The same check runs at upload and re-read (`units.find`, which shares its code with the fix, over the stored chunks, as answers see them) and lists the suspected misprints on the document: a **N unit fixes** badge on its library card and in the table view's Units column opens the list, with the page (for PDFs, a link to that page of the original, page 1 included), the document's own text before the figures, what the document printed, what models read instead, and the kind (quarts printed as gallons, imperial gallons printed as U.S., or a pair that just disagrees). The first 500 findings are kept per document and all of them are counted, so a table whose figures all disagree can't swell the library listing; the list then says how many it shows. Documents indexed before this get their check once, from their stored text, when the app starts (no model calls), and so does every document whenever `app/units.py` changes, so the lists always match what answers get; documents read before page breaks were kept show no page. Pairs printed side by side in a table (`| 8.9 ℓ, 2.4 U.S.gal | 8.3 ℓ, 2.2 U.S.gal |`) are kept apart: a figure already paired with the one before it is not paired with the next cell's. API: `unit_fixes` (a count, `null` while unchecked) in `GET /api/documents`; `GET /api/documents/<id>/units` for the list (`findings`, and `total` counting them all) |
| Table view | The **Table** button in the library opens every document in a sortable, filterable table (DataTables, served from `app/static/vendor`, so it works offline). Tick rows, or the header box to tick everything the current filter shows, then delete them all at once, re-read them, or **Ask about** them. The Units column shows each document's unit fixes |
| Backups | A `backup` service (`app/backup.py`) takes a checked, compacted snapshot of the database every night with SQLite's backup API, from the library mounted read-only, keeps the newest `BACKUP_KEEP` (14), and adds new originals to a copy that is never pruned, so deleted documents stay recoverable. `docker compose run --rm restore <snapshot>` puts one back. See **Backups** below |
| Login | Optional. Set `APP_PASSWORD` and everyone is asked for that one shared password (there are no user accounts); unset or empty, there is no login and nothing changes. Without a session, pages go to a small login page (`/login`) and come back after it, a bookmarked link to an original file too (a link to one of its pages keeps the page), and API calls get 401 `{"error": "Login required", "login": true}`, on which the page goes to the login page, which says the session has ended (say after **Log out** in another tab): a question or new instruction being sent then is back in its box after logging in (kept in that tab's sessionStorage), while an upload has to be chosen again. Logging in gives a signed session cookie (`docchat_session`, HttpOnly, SameSite=Lax) that lasts `SESSION_DAYS` (30) days from then; it is not renewed by use. **Log out** in the header ends it in that browser and forgets the Claude key typed into the page there; an answer being written is stopped first, and kept as far as it was shown. Where the header is short of room (500 px and narrower, and 821-910 px, beside the library) Log out is an exit icon and Instructions reads **Rules**. The cookie is signed with `SECRET_KEY`, or else with a random key made at the first request once the app runs with a password, and kept beside the database in `/data/secret_key` (mode 600), so restarts and rebuilds don't log anyone out. Changing `APP_PASSWORD` or `SECRET_KEY`, or deleting `/data/secret_key` and restarting, logs everyone out. After 5 wrong passwords from one address within 10 minutes, that address waits a minute after each further failure, the right password included (429 with `Retry-After`); wrong passwords are logged with the address. Behind Docker's published port (and the Windows port proxy), every client arrives from the same address, Docker's gateway, so in practice a minute's wait holds up everyone, and someone who keeps trying a wrong password once a minute keeps it going for as long as they like. Sessions already logged in carry on meanwhile, and restarting the app (`docker compose restart chatbot`) clears the count, which is kept in memory. Logged in, every API call that changes something (POST, PATCH, DELETE) must carry an `X-Requested-With` header, any value, or it gets 403: the page sends it, and a page on another site can't add it (that would need CORS, which the server never grants), so it can't use a logged-in browser to change anything here. Requests whose `Origin` names another site still get 403 too, login or not. Background jobs and the work done at start (resumed jobs, embeddings, unit checks) don't pass through the login. API clients log in once and keep the cookie: `curl -c jar --data-urlencode 'password=…' http://host:8000/login` (`--data-urlencode`, so a `+`, `&` or `%` in the password arrives as typed; `-d` sends it unencoded, and it fails as a wrong password), then for example `curl -b jar -H "X-Requested-With: curl" -F file=@manual.pdf http://host:8000/api/upload` |

## Keeping token use down

- **Retrieval instead of whole documents:** a chat turn sends only the top-K passages (`TOP_K`, default 5, about 1,500 characters each), not entire files. Search by meaning runs on the local embedding model, so it adds nothing to a Claude bill.
- **Prompt caching:** chat requests set `cache_control`, so the system prompt and the earlier conversation are read from cache (5% of the normal input price on Opus and Sonnet 5.5, 2.5% on Fable 5.2, 10% on Haiku 5.5). The server keeps each question exactly as it was sent and replays the earlier turns from the saved conversation, so the prefix stays byte-identical; streamed and whole answers send the same request, so they share the cache. Each answer shows how many tokens were read from and written to the cache. **Stop** closes the stream of an answer you don't need, which ends it there.
- **Bounded analysis:** one analysis call sends at most `CLAUDE_ANALYZE_CHARS` (default 500,000) characters to Claude, or `OLLAMA_ANALYZE_CHARS` (default 40,000) to a local model, which has a much smaller context window (fewer for text dense in figures, as it is sized by its tokens). Longer documents are analyzed in sections of that size, so the analysis reads the whole text, up to `ANALYZE_MAX_SECTIONS` sections (default 24); past that it samples. The full text is always indexed and searchable either way. A 500,000-character section is roughly 125,000-170,000 input tokens, so analyzing a very long document costs noticeably more on Opus than on Haiku or Sonnet; the estimate counts every section, and lowering `ANALYZE_MAX_SECTIONS` caps what one document can cost.
- **PDF reading costs tokens:** each page Claude reads is billed as an image plus its text (roughly 1,500 to 3,000 input tokens), and the transcription is billed as output. By default Claude reads only scanned pages, so a PDF with a text layer costs just its metadata call. Leave **Claude reads every page** off unless the layout needs it, pick Claude Haiku 5.5 under "Read with" to make reading cheap, or use a local model to spend nothing. Jobs estimated at `CONFIRM_COST_USD` or more wait for a confirmation.
- **Low effort by default:** `CLAUDE_EFFORT=low`. Raise it if you want more careful answers.

## Backups

The `backup` service in `docker-compose.yml` (the same image, running `python -m app.backup`) backs up the library every night at `BACKUP_HOUR` into the `backups` volume:

- **The database:** a snapshot of `/data/metabase.db` made with SQLite's backup API, which reads it in one read transaction, so an upload or an answer being saved at that moment is either all in it or not at all (a file copy could catch it half written). The copy is compacted (`VACUUM`: the live file keeps the space deleted documents freed, and the live library's 97 MB came to 8 MB), checked (`PRAGMA integrity_check`), and only then named `metabase-YYYYMMDD-HHMM.db`. The newest `BACKUP_KEEP` (14) are kept; older ones are deleted, and other files in the volume are left alone.
- **The originals:** each file in `/data/files` that the backup doesn't have yet is copied to `files/` in the volume, and checked against the SHA-256 in its name. Copies are only ever added, so the original of a deleted document stays recoverable. The volume grows by every distinct file ever uploaded; delete old ones by hand if you need the room.

The service mounts the library read-only and opens the database read-only (`mode=ro`), so it can't change either. The hour is the container's, which is UTC unless you set `TZ`: for 3 a.m. in New York, put `TZ=America/New_York` in `.env`. The service looks at the clock every minute and backs up when no snapshot has been taken since the last `BACKUP_HOUR`: a night the machine was off or asleep is made up soon after it is back, and the first snapshot is taken as soon as the service first starts. A failed backup is logged and tried again 30 minutes later. `docker compose logs backup` shows each one.

```bash
docker compose exec backup python -m app.backup --now    # take one now
docker compose exec backup python -m app.backup --list   # list the snapshots and originals
docker compose cp backup:/backups/. /mnt/d/chatbot-backups   # copy them out of Docker, to another disk
```

The `backups` volume is on the same disk as the library (inside WSL's virtual disk on Windows), so it guards against mistakes and a damaged database, not against losing the disk. Copy it somewhere else now and then: another disk (`/mnt/d/...` is the D: drive from WSL), or a USB drive. Not into the repo folder: the copy holds every document's text, the conversations and the original files, and a `git add` could take them to GitHub (`.gitignore` covers a `backups/` folder there, but no other name).

To restore a snapshot:

```bash
docker compose stop chatbot                                 # the app keeps some of the library's state in memory
docker compose run --rm restore                             # lists the snapshots
docker compose run --rm restore metabase-20261112-0300.db   # or: latest
docker compose restart chatbot
```

The `restore` service isn't started by `up`; `docker compose run` builds it from the current code and starts it on its own. It refuses while the app is running: the app holds a lock on `/data/app.lock` for as long as it runs, and waits for a restore under way to finish before it starts. It checks the snapshot, puts it back as `/data/metabase.db`, keeps the database it replaces beside it as `metabase.db.before-restore-<time>` (delete that once you're happy), and copies back the originals the snapshot's documents use that `/data/files` lacks. Anything saved after the snapshot was taken (uploads, conversations, usage) is not in it. A snapshot from an older version of the app is brought up to date when the app starts, like any older library. The login's `/data/secret_key` is not backed up: restored onto a new machine, everyone logs in again.

## Reach it from the LAN (Windows with WSL)

When Docker runs inside WSL, other machines reach the app through a Windows port proxy (`0.0.0.0:8000` to WSL's address, port 8000) and an inbound firewall rule, **Chatbot 8000**. WSL gets a new address when it restarts, which leaves the proxy pointing nowhere. WSL's mirrored networking would make the proxy unnecessary, but it needs Windows 11 22H2 or later, and this machine has 21H2 (build 22000). Instead, `scripts/portproxy.ps1`:

1. starts the WSL distro (`vostok`) if it isn't running, and keeps it running with a hidden `wsl.exe -d vostok --exec sleep infinity` (WSL stops a distro soon after its last window closes; Docker and the containers, all `restart: unless-stopped`, start with the distro);
2. reads the distro's address (`hostname -I`, the first one);
3. adds or updates the port proxy rule for `0.0.0.0:8000` if it points anywhere else;
4. makes sure the IP Helper service, which carries the port proxy, is running, and that the firewall rule exists (it adds one for TCP 8000 if there is none, and leaves a disabled one disabled).

Run again, it changes nothing. It logs what it did to `C:\ProgramData\Chatbot\portproxy.log`. A step that fails (IP Helper won't start, say, or the keepalive ends at once) is logged, the other steps still run, and the script ends with exit code 1, which the task shows as its last result. Other port proxy rules are left alone.

One-time setup, from an **elevated** PowerShell (Run as administrator) in the repo folder:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\install-portproxy-task.ps1
```

This copies `portproxy.ps1` to `C:\ProgramData\Chatbot`, a folder only administrators can change (the task runs the script with full rights; any user may create folders in `C:\ProgramData`, so if this one is there already, Administrators take it over and its permissions are reset, and the install stops if it can't make sure of that), and registers the scheduled task **Chatbot portproxy**. The task runs it as you, with highest privileges, at startup (30 seconds after boot, whether anyone is logged on or not, with no password stored) and at logon. The install then runs the task once and shows its log. Run the install again after changing `portproxy.ps1`.

- To see what it would do, without changing anything: `powershell -ExecutionPolicy Bypass -File .\scripts\portproxy.ps1 -DryRun` (or `-WhatIf`). This works without elevation; without elevation and without `-DryRun`, the script refuses to run. Reading WSL's address starts WSL if it isn't running, even in a dry run.
- `wsl --shutdown` gives WSL a new address: afterwards, run `Start-ScheduledTask -TaskName 'Chatbot portproxy'`, or log off and on again.
- If the log shows WSL failing to start in the startup run, Windows didn't let WSL start with nobody logged on: run the install again with `-Interactive`, which runs the task at logon only, in your session.
- Both scripts take `-Distro` and `-Port`; `install-portproxy-task.ps1 -WhatIf` shows the task it would register.
- To remove the task: `install-portproxy-task.ps1 -Remove`. It leaves the port proxy and firewall rules, and prints the `netsh` commands that remove them.

pip install -r requirements.txt pytest pillow
DB_PATH=data/metabase.db flask --app app.main run --debug
