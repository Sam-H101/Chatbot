# Document Chatbot (PoC)

A small standalone chatbot that answers questions with the Claude API, using your own API key. You upload documents, Claude pulls metadata out of each one (title, type, summary, keywords), and everything goes into an embedded SQLite database with full-text search. When you ask a question, the app finds the most relevant passages and sends them along with it.

## Run it

By default the app runs on local models through [Ollama](https://ollama.com), on your own NVIDIA GPU: no API key, and documents never leave the machine. The defaults are sized for an 11 GB card (GTX 1080 Ti):

- `qwen3.5:9b` (about 6.6 GB) answers questions and extracts metadata.
- `minicpm-v4.6` (about 1.6 GB) reads scanned PDF pages. Pages that have embedded text skip the model.

Containers need the NVIDIA Container Toolkit to use the GPU (one-time setup, inside WSL on Windows). See NVIDIA's install guide, then run `sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker`.

```bash
docker compose up --build -d
docker compose exec ollama ollama pull qwen3.5:9b
docker compose exec ollama ollama pull minicpm-v4.6
```

Open http://localhost:8000 and upload some files.

To use the Claude API instead, run `LLM_BACKEND=claude docker compose up --build` and paste your Claude API key into the page. The rest of this README describes both backends. Token and caching notes apply to Claude.

The key stays in your browser's localStorage and goes along with each request. The server never stores it. If you'd rather set it on the server, export `ANTHROPIC_API_KEY` before running `docker compose up`.

The database is a single file, `/data/metabase.db`, kept in the `metabase` Docker volume. No database server is needed. The original uploaded files are kept beside it, in `/data/files`. Uploads are read in the background by one worker thread, which is why gunicorn runs a single worker process (see the Dockerfile). The thread starts with the app (`app/gunicorn_conf.py`), and its queue lives in the database.

## What it does

| Feature | How |
|---|---|
| Upload | PDF (text or scanned), DOCX, and any UTF-8 text file (txt, md, csv, json, code…). The upload only sends and stores the file (with a progress bar while it travels); reading happens in the background, see the next row. A file that can never be read (a PDF that doesn't open, a damaged DOCX, a file that isn't UTF-8 text, or one with no text at all) gets a 400 at once and is not queued or kept |
| Background reading | Each upload becomes a job in the `jobs` table, and one worker thread reads the jobs in order. The upload list shows each job live: its stage ("Reading page 40 of 312", "Analyzing with …") and a progress bar, then **Added · model** (or the reason Auto switched to Claude). A queued job waits still; only the one being read moves. On a phone, where the list is in the closed drawer, the ☰ button counts the jobs under way and turns red when one waits for you (failed, or a cost to confirm). Jobs survive a page reload: the list comes back from `GET /api/jobs`. A running job can be cancelled (it stops after its current page). A failed job shows its error with **Retry**; pages a model already read are kept with the job, so a retry, or a job cut off by a restart, carries on where it stopped and doesn't pay for those pages twice. Jobs left running by a restart are queued again as soon as the app is back up, with no need to open the page. API: `POST /api/upload` answers 202 `{job}`; `GET /api/jobs`, `GET /api/jobs/<id>`, `POST /api/jobs/<id>/cancel`, `/retry` and `/confirm` |
| PDF reading | Every reader returns one text per page, and a document's text keeps its pages apart with a form feed (`\f`), so a chunk's page can be worked out later; search, excerpts and analysis treat it as a paragraph break. Other files have no pages: a form feed in a text file is stored as a line break. Local models: pages with a text layer are taken as they are, and the vision model (`OLLAMA_VISION_MODEL`) reads only scanned pages. Claude: by default (`CLAUDE_PDF_PAGES=scanned`) the same: only scanned pages go to Claude, as a new PDF of just those pages, with their page numbers in the prompt. The **Claude reads every page** box beside "Read with" (shown for Claude models) has Claude read every page as text and image instead, which is worth its cost for complex tables and layouts. Claude reads `PDF_PAGES_PER_CALL`-page pieces in parallel. A page counts as scanned when its text layer has fewer than `MIN_PAGE_CHARS` visible characters |
| Cost estimate | Before a job reads with Claude, it estimates the cost: pages, pages Claude reads, about 2,000 input and 600 output tokens per page Claude reads, plus the analysis (about 4 characters a token; a text longer than `CLAUDE_ANALYZE_CHARS` adds one call per section, counted as the analysis will split it, pages kept whole, about 1,000 output tokens of notes each, and one combining them), priced with `PRICES` in `app/llm.py`. A Claude model missing from `PRICES` is estimated at the dearest price listed there, and the row says so. The upload row shows the estimate. At `CONFIRM_COST_USD` (default $1.00) or more, the job waits for **Start** or **Cancel**. **Start** covers the amount shown: a retry that would cost more asks again. Auto only estimates Claude when it actually switches to it, and when only the local analysis failed, the estimate covers just Claude's analysis of the text read locally |
| Re-read | In the **Table** view, tick documents and pick **Re-read with** (any model, with the same every-page box for Claude): their kept originals are read again and each document's text, metadata and model are replaced in place, keeping its id and upload date. If the new analysis fails (a refusal, an API still overloaded after its retries, a local reply that isn't JSON), the re-read fails and the document keeps everything it had; **Retry** redoes only the analysis, since the pages read are kept. Documents uploaded before originals were kept can't be re-read. API: `POST /api/documents/<id>/reread` with `{"model": "…", "claude_pages": "scanned" \| "all"}` |
| Analyze | Structured JSON output: title, doc type, summary, keywords. A document that fits one call (`CLAUDE_ANALYZE_CHARS` for Claude, `OLLAMA_ANALYZE_CHARS` for a local model, kept within `OLLAMA_NUM_CTX`) takes one call. A longer one is analyzed section by section (`app/sections.py`): it is split into sections of about equal size at page breaks, or else at paragraphs, each within that limit; the same model takes notes on each section (key topics, specifications and values, procedures, warnings), and a last call turns the notes into the metadata, so the whole document counts, not just its start. For a local model, sections are sized by an estimate of their tokens, with a token for every digit as qwen3.5 counts them (tables of figures run at about 1.3 characters a token, prose at 4), and Ollama is asked to refuse a prompt too long for its context rather than silently drop its start; text that is still too dense is read again in smaller pieces. When the notes are too long for one local call, neighbouring notes are merged first; a merge whose reply can't be used leaves its notes as they were and merges fewer at a time. The upload list shows each step ("Analyzing section 3 of 12 with …", "(sampled from 61)" when sampling, "Combining the notes of 12 sections"), every call is in the usage log, and each section's notes are kept with the job, so a retry doesn't ask for them again. At most `ANALYZE_MAX_SECTIONS` (default 24) sections are read: a document needing more is sampled evenly from first to last section, and marked `partial: 24 of 61 sections, 39% of the text` (shown on the library card). A section whose reply can't be used (not JSON, cut off, a refusal) is left out and counted the same way. File names are cut to 200 characters in the prompts. If the analysis fails, a new upload is still added and searchable, marked `none: <reason>`; a re-read, or an upload replacing its duplicates, fails instead, so no metadata is lost. Documents analyzed before this was added and marked just `partial` were analyzed from their start only; a re-read covers them whole |
| Metadata base | SQLite tables `documents` and `chunks`, plus FTS5 indexes over the metadata and the full text (porter stemming), and `jobs`, `usage` and `instructions`. Older databases gain new columns and tables automatically when the app starts; their documents keep working without a kept file, hash, page breaks or unit check |
| Originals | Every uploaded file is kept in `FILES_DIR` (default `/data/files`), stored once per distinct content and named by its SHA-256. **Open** in the library and in the table view shows it: PDFs open in the browser's viewer and plain text as text; other types download. `GET /api/documents/<id>/file` serves it. Deleting a document removes its file once no other document uses it. Documents uploaded before originals were kept have no file and no Open link |
| Duplicates | Uploads are hashed (SHA-256). If the same file is already in the library, the upload stops before any model reads it, and its row in the upload queue asks: **Replace** (read the new upload, then delete the earlier copies), **Keep both**, or **Skip**. Through the API: the form field `on_duplicate` is `replace` or `keep`; without it the answer is 409 with the earlier copy's id, file name, date and model. A copy that is still queued or being read also counts (say the file was picked twice): the 409 then has `in_progress: true`, and only **Keep both** or **Skip** are offered. Documents uploaded before hashing never count as duplicates |
| Usage | Every model call (reading PDF pages, analyzing a document, each section of a long one included, answering) is logged with its model, tokens and cost in the `usage` table as it happens, including calls made by uploads that then failed and Claude answers that ended in a refusal. Calls made by a job carry its `job_id` and are linked to the document when the job finishes (failed attempts before a successful retry too). Deleting a document keeps its rows but clears their `doc_id`, because SQLite reuses ids. The **Usage** button shows totals per model and per day for the last 7, 30, 90 or 365 days; `GET /api/usage?days=30` returns the same. Claude costs come from the list prices in `PRICES` in `app/llm.py` and are estimates, not the invoice. Cache reads have their own price per model (5% of the input price on Opus and Sonnet 5.5, 2.5% on Fable 5.2, 10% on Haiku 5.5), and cache writes cost 1.25x the input price. Models missing from the table count as $0. Local models cost nothing. If the log can't be written (say the database stays locked), the answer or upload still goes through and the error goes to the server log |
| Search | The sidebar search box matches documents by metadata and lists matching passages with highlighted snippets |
| Chat | Each question runs a full-text search for the top 5 passages, which go into the prompt. Answers cite file names |
| Model pickers | "Read with" (in the upload box) picks the model that reads and analyzes uploads; "Answer with" (under the question box) picks the chat model. Each offers **Auto**, every model pulled into Ollama, and the Claude models. The page remembers both choices, and every answer and upload shows which model did the work |
| Auto | Uses the local model (`OLLAMA_MODEL`) and switches to Claude (`CLAUDE_MODEL`) when Ollama is down or errors, or when a chat prompt is too long for `OLLAMA_NUM_CTX` (estimated with a token for every digit, as for analysis). It only switches when a Claude key is available (browser or server), and says why it switched. For an upload, Claude reads the file only if the local reading failed; if just the local analysis failed, Claude analyzes the text the local models already read |
| Instructions | The **Instructions** button holds rules added to the system prompt of every question, for local models and Claude alike (for example how to handle units). Each can be switched on or off, and they are stored in the database, so they apply to everyone using the app |
| Unit checks | Before passages go to the model, litre and gallon figures printed side by side are checked against each other (`app/units.py`). If they disagree, the litre figure is trusted and the gallon figure is recalculated; a quarts-printed-as-gallons misprint is shown as quarts. The stored document text is not changed. The same check runs at upload and re-read (`units.find`, which shares its code with the fix, over the stored chunks, as answers see them) and lists the suspected misprints on the document: a **N unit fixes** badge on its library card and in the table view's Units column opens the list, with the page (for PDFs, a link to that page of the original, page 1 included), the document's own text before the figures, what the document printed, what models read instead, and the kind (quarts printed as gallons, imperial gallons printed as U.S., or a pair that just disagrees). The first 500 findings are kept per document and all of them are counted, so a table whose figures all disagree can't swell the library listing; the list then says how many it shows. Documents indexed before this get their check once, from their stored text, when the app starts (no model calls), and so does every document whenever `app/units.py` changes, so the lists always match what answers get; documents read before page breaks were kept show no page. Pairs printed side by side in a table (`| 8.9 ℓ, 2.4 U.S.gal | 8.3 ℓ, 2.2 U.S.gal |`) are kept apart: a figure already paired with the one before it is not paired with the next cell's. API: `unit_fixes` (a count, `null` while unchecked) in `GET /api/documents`; `GET /api/documents/<id>/units` for the list (`findings`, and `total` counting them all) |
| Table view | The **Table** button in the library opens every document in a sortable, filterable table (DataTables, served from `app/static/vendor`, so it works offline). Tick rows, or the header box to tick everything the current filter shows, then delete them all at once. The Units column shows each document's unit fixes |

## Keeping token use down

- **Retrieval instead of whole documents:** a chat turn sends only the top-K passages (`TOP_K`, default 5, about 1,500 characters each), not entire files.
- **Prompt caching:** chat requests set `cache_control`, so the system prompt and the earlier conversation are read from cache (5% of the normal input price on Opus and Sonnet 5.5, 2.5% on Fable 5.2, 10% on Haiku 5.5). The browser sends back the exact earlier turns so the prefix stays byte-identical. Each answer shows how many tokens were read from and written to the cache.
- **Bounded analysis:** one analysis call sends at most `CLAUDE_ANALYZE_CHARS` (default 500,000) characters to Claude, or `OLLAMA_ANALYZE_CHARS` (default 40,000) to a local model, which has a much smaller context window (fewer for text dense in figures, as it is sized by its tokens). Longer documents are analyzed in sections of that size, so the analysis reads the whole text, up to `ANALYZE_MAX_SECTIONS` sections (default 24); past that it samples. The full text is always indexed and searchable either way. A 500,000-character section is roughly 125,000-170,000 input tokens, so analyzing a very long document costs noticeably more on Opus than on Haiku or Sonnet; the estimate counts every section, and lowering `ANALYZE_MAX_SECTIONS` caps what one document can cost.
- **PDF reading costs tokens:** each page Claude reads is billed as an image plus its text (roughly 1,500 to 3,000 input tokens), and the transcription is billed as output. By default Claude reads only scanned pages, so a PDF with a text layer costs just its metadata call. Leave **Claude reads every page** off unless the layout needs it, pick Claude Haiku 5.5 under "Read with" to make reading cheap, or use a local model to spend nothing. Jobs estimated at `CONFIRM_COST_USD` or more wait for a confirmation.
- **Low effort by default:** `CLAUDE_EFFORT=low`. Raise it if you want more careful answers.

## Configuration

| Env var | Default | |
|---|---|---|
| `LLM_BACKEND` | `ollama` | Default when the page sends no model choice: `ollama` means Auto, `claude` means `CLAUDE_MODEL` |
| `OLLAMA_URL` | `http://ollama:11434` (compose) | Where Ollama listens. Point it elsewhere to use an Ollama server outside compose |
| `OLLAMA_MODEL` | `qwen3.5:9b` | Chat and metadata model |
| `OLLAMA_VISION_MODEL` | `minicpm-v4.6` | Reads scanned PDF pages. `qwen3.5:9b` also reads images, so set it to that to run a single model |
| `OLLAMA_NUM_CTX` | `16384` | Context window per request. About the most an 11 GB card fits next to a 9B model. Analysis calls never go past it: Ollama is told to refuse a longer prompt rather than cut it, and the text is then read in smaller pieces |
| `MIN_PAGE_CHARS` | `20` | A PDF page with less embedded text than this counts as scanned: the vision model reads it (Ollama), and so does Claude when `CLAUDE_PDF_PAGES=scanned` |
| `CLAUDE_PDF_PAGES` | `scanned` | Which PDF pages Claude reads: `scanned` (only pages without a usable text layer; the text layer is used for the rest) or `all` (every page, as text and image). The default for the page's **Claude reads every page** box; uploads can send `claude_pages` to override it. Any other value is logged at start and treated as `scanned` |
| `CONFIRM_COST_USD` | `1.00` | A job whose Claude reading is estimated to cost this much or more waits for **Start** in the upload list. `0` asks for every Claude job |
| `ANTHROPIC_API_KEY` | (none) | Optional server-side key |
| `CLAUDE_MODEL` | `claude-opus-5-5` | Claude model Auto switches to, and the default when `LLM_BACKEND=claude`. Any Claude model can also be picked in the page |
| `CLAUDE_EFFORT` | `low` | `low` / `medium` / `high` / `xhigh` / `max` |
| `SYSTEM_PROMPT` | built-in | Gives the bot its personality |
| `CLAUDE_ANALYZE_CHARS` | `500000` | Characters of a document one Claude analysis call reads. Longer documents are analyzed in sections of at most this size |
| `OLLAMA_ANALYZE_CHARS` | `40000` | The most characters one local analysis call reads. Sections are also kept within the tokens `OLLAMA_NUM_CTX` holds next to the prompt and a 2,000-token reply, estimated with a token for every digit (qwen3.5 splits numbers into digits), so tables of figures make smaller sections than prose. Raise it together with `OLLAMA_NUM_CTX` |
| `ANALYZE_MAX_SECTIONS` | `24` | Most sections (one model call each) one document's analysis reads. A document needing more is sampled evenly and marked `partial: <read> of <sections> sections, <share> of the text` |
| `TOP_K` | `5` | Passages retrieved for each question |
| `PDF_EXTRACTOR` | `model` | `model` lets the chosen model read PDFs (scanned pages only, unless Claude is told to read every page). `local` uses only the PDF's embedded text layer, so scanned pages come out empty |
| `PDF_PAGES_PER_CALL` | `20` | Pages per Claude call when reading a PDF |
| `PDF_CONCURRENCY` | `4` | PDF pieces read at the same time |
| `MAX_UPLOAD_MB` | `200` | Maximum upload size. The page checks it before uploading |
| `PDF_MAX_BATCH_MB` | `20` | Largest PDF piece sent to Claude in one request (about 27 MB once base64-encoded, under the API's 32 MB limit). Pieces over it are split further |
| `DB_PATH` | `/data/metabase.db` | Location of the SQLite file |
| `FILES_DIR` | `files` next to `DB_PATH` (`/data/files`) | Where the original uploads are kept, one file per distinct content, named by its SHA-256 |

Requests turn on server-side refusal fallbacks (`fallbacks: "default"`). If Claude's safety filter declines a request, the API retries it on a fallback model instead of failing.

## Develop without Docker

```bash
pip install -r requirements.txt pytest
DB_PATH=data/metabase.db flask --app app.main run --debug
pytest
```

## Not done yet

- Batch analysis for bulk uploads (the Message Batches API is 50% cheaper but asynchronous)
- Semantic or embedding search (FTS5 matches keywords, not meaning)
- Authentication (anyone who can reach the port can see the documents). Only one thing is guarded: a page on another site can't make a visitor's browser change anything here. Browsers name the sending page's origin on every POST, PATCH and DELETE, and requests naming another site get 403. Clients that send no origin, such as curl, are let through
