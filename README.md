# Document Chatbot (PoC)

A small standalone chatbot that answers questions with the Claude API, using your own API key. You upload documents, Claude pulls metadata out of each one (title, type, summary, keywords), and everything goes into a PostgreSQL database with full-text search and vector search (pgvector). When you ask a question, the app finds the most relevant passages and sends them along with it.

## Run it

By default the app runs on local models through [Ollama](https://ollama.com), on your own NVIDIA GPU: no API key, and documents never leave the machine. The defaults are sized for an 11 GB card (GTX 1080 Ti):

- `qwen3.5:9b` (about 6.6 GB) answers questions and extracts metadata.
- `minicpm-v4.6` (about 1.6 GB) reads scanned PDF pages. Pages that have embedded text skip the model.
- `qwen3-embedding:0.6b` (about 640 MB) turns passages and questions into vectors, so questions are also searched by meaning. Without it, search is by keywords only.

Containers need the NVIDIA Container Toolkit to use the GPU (one-time setup, inside WSL on Windows). See NVIDIA's install guide, then run `sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker`.

```bash
docker compose up --build -d
docker compose exec ollama ollama pull qwen3.5:9b
docker compose exec ollama ollama pull minicpm-v4.6
docker compose exec ollama ollama pull qwen3-embedding:0.6b
```

Open http://localhost:8000 and upload some files.

To use the Claude API instead, run `LLM_BACKEND=claude docker compose up --build` and paste your Claude API key into the page. The rest of this README describes both backends. Token and caching notes apply to Claude.

The key stays in your browser's localStorage and goes along with each request. The server never stores it. If you'd rather set it on the server, export `ANTHROPIC_API_KEY` before running `docker compose up`.

Everyone signs in with an account of their own. The first time you open the app it asks you to make the first account, with a one-time setup code the app writes in its log, so someone else on the network can't claim the library before you: `docker compose logs chatbot | grep "setup code"` (or `docker compose exec chatbot python -m app.users setup-code`). Signed in, add the others under your name in the header, **Users and passwords**. There are no roles: whoever signs in can do anything, adding and deleting users included. See **Sign-in** below.

The database is PostgreSQL 18 with pgvector, in the `postgres` service (its data in the `pgdata` volume; not published to the host, only the app and its backup services reach it). Set `POSTGRES_PASSWORD` in `.env` before the first start: it is set when the data volume is first made. The original uploaded files are kept in `/data/files` (the `metabase` volume), or in an S3 bucket or Azure Blob container (see **Where originals are kept**). A library from before Postgres is moved over once with `python -m app.migrate` (see **Moving from SQLite**). Uploads are read in the background by one worker thread, which is why gunicorn runs a single worker process (see the Dockerfile). The thread starts with the app (`app/gunicorn_conf.py`), and its queue lives in the database. `docker compose up` also starts a `backup` service that backs up both every night (see **Backups**). On Windows, where Docker runs inside WSL, see **Reach it from the LAN** for keeping port 8000 open to other machines across restarts.

## What it does

| Feature | How |
|---|---|
| Upload | PDF (text or scanned), DOCX, photos (JPG, PNG, WebP, and HEIC when `pillow-heif` is installed, as it is in the image), Markdown (`.md`, `.markdown`) and any UTF-8 text file (txt, csv, json, code…). The upload only sends and stores the file (with a progress bar while it travels); reading happens in the background, see the next row. A file that can never be read (a PDF that doesn't open, a damaged DOCX, a photo that isn't a JPG, PNG, WebP or HEIC image or has over 50 megapixels, a file that isn't UTF-8 text, or one with no text at all) gets a 400 at once and is not queued or kept. An upload goes into a folder (form field `folder_id`; empty for Unfiled; 404 `{"error": "That folder was deleted", "folder_gone": true}` if it is gone), and into Unfiled it may be filed automatically (`auto_file`, `1` by default, see Auto-filing). `GET /api/models` lists the extensions the file picker offers (`upload_types`: `extensions`, and `heic`). In the page: **Add files** in the left column, or drop files anywhere, go into the place Documents shows (a folder; Unfiled from Chat, Library, Unfiled and All documents, where **Auto-file into a matching folder** sets `auto_file`; the box says where, "Into Tractor › Manuals"); files dropped onto a folder (in the tree, a folder tile or a breadcrumb) go into it, and a folder dropped from the computer is refused with a note. On a phone, **+ Add** in Documents opens the same choices, with **Take a photo** (the camera; the photo is named for when it was taken). A file the server already has gets **Replace** (the new copy keeps the old one's folder), **Keep both** or **Skip**, the row naming where the copy is |
| Background reading | Each upload becomes a job in the `jobs` table, and one worker thread reads the jobs in order. The upload list shows each job live: its stage ("Reading page 40 of 312", "Analyzing with …", "Indexing for search by meaning: 64 of 120 passages") and a progress bar, then **Added · model** (or the reason Auto switched to Claude). A queued job waits still; only the one being read moves. Each row says where its file is going ("→ Tractor › Manuals", "→ Unfiled · auto-file") and, once read, where it went: "Filed in **Receipts** automatically" with **Undo** (that row stays until hidden, so files dropped in and left show where they went), "Suggested folder: Receipts" with **Move to Receipts** (or **Move to new folder 'Receipts'**), "Added to Tractor › Manuals" or "Replaced · stays in …", each with **Show**, which opens the document in Documents. Meanwhile the place it goes to shows a dashed placeholder card with the job's stage; a click on it finds its row. The list sits under the Add box; on a phone it is the **Uploads** box at the top of Documents, which opens by itself once when a row starts needing you, and the folder button at the top left counts the jobs under way and turns red when one waits for you (failed, a duplicate, or a cost to confirm). Jobs survive a page reload: the list comes back from `GET /api/jobs`. A running job can be cancelled: a call to a local model it waits on is cut off at once (Ollama stops working on it, and the next job starts), and otherwise it stops after its current page or Claude call. A failed job shows its error with **Retry**; pages a model already read are kept with the job, so a retry, or a job cut off by a restart, carries on where it stopped and doesn't pay for those pages twice. Jobs left running by a restart are queued again as soon as the app is back up, with no need to open the page. API: `POST /api/upload` answers 202 `{job}`; `GET /api/jobs`, `GET /api/jobs/<id>`, `POST /api/jobs/<id>/cancel`, `/retry` and `/confirm` |
| PDF reading | Every reader returns one text per page, and a document's text keeps its pages apart with a form feed (`\f`), so every chunk records the pages it spans (`page_start`, `page_end`) for citations; search and analysis treat it as a paragraph break. Other files have no pages: a form feed in a text file is stored as a line break. Local models: pages with a text layer are taken as they are, and the vision model (`OLLAMA_VISION_MODEL`) reads only scanned pages. Claude: by default (`CLAUDE_PDF_PAGES=scanned`) the same: only scanned pages go to Claude, as a new PDF of just those pages, with their page numbers in the prompt. The **Claude reads every page** box beside "Read with" (shown for Claude models) has Claude read every page as text and image instead, which is worth its cost for complex tables and layouts. Claude reads `PDF_PAGES_PER_CALL`-page pieces in parallel. A page counts as scanned when its text layer has fewer than `MIN_PAGE_CHARS` visible characters |
| Cost estimate | Before a job reads with Claude, it estimates the cost: pages, pages Claude reads, about 2,000 input and 600 output tokens per page Claude reads, plus the analysis (about 4 characters a token; a text longer than `CLAUDE_ANALYZE_CHARS` adds one call per section, counted as the analysis will split it, pages kept whole, about 1,000 output tokens of notes each, and one combining them), priced with `PRICES` in `app/llm.py`. A Claude model missing from `PRICES` is estimated at the dearest price listed there, and the row says so. A photo is one call reading it (about width x height / 750 tokens at the 1,568-pixel size it is sent at, 1,600 at most, plus 300 for the prompt, and 600 written) and the analysis of about 2,400 characters; its estimate has `"image": true`. The upload row shows the estimate. At `CONFIRM_COST_USD` (default $1.00) or more, the job waits for **Start** or **Cancel**. **Start** covers the amount shown: a retry that would cost more asks again. Auto only estimates Claude when it actually switches to it, and when only the local analysis failed, the estimate covers just Claude's analysis of the text read locally |
| Re-read | **Re-read…** on a document (its detail or ⋯ menu), or on documents selected in Documents, asks which model (any, with the same every-page box for Claude): their kept originals are read again and each document's text, metadata and model are replaced in place, keeping its id and upload date. If the new analysis fails (a refusal, an API still overloaded after its retries, a local reply that isn't JSON), the re-read fails and the document keeps everything it had; **Retry** redoes only the analysis, since the pages read are kept. Documents uploaded before originals were kept can't be re-read. API: `POST /api/documents/<id>/reread` with `{"model": "…", "claude_pages": "scanned" \| "all"}` |
| Analyze | Structured JSON output: title, doc type, summary, keywords, the key details (next row) and a folder to file it in (see Auto-filing). A document that fits one call (`CLAUDE_ANALYZE_CHARS` for Claude, `OLLAMA_ANALYZE_CHARS` for a local model, kept within `OLLAMA_NUM_CTX`) takes one call. A longer one is analyzed section by section (`app/sections.py`): it is split into sections of about equal size at page breaks, or else at paragraphs, each within that limit; the same model takes notes on each section (key topics, specifications and values, procedures, warnings), and a last call turns the notes into the metadata, so the whole document counts, not just its start. For a local model, sections are sized by an estimate of their tokens, with a token for every digit as qwen3.5 counts them (tables of figures run at about 1.3 characters a token, prose at 4), and Ollama is asked to refuse a prompt too long for its context rather than silently drop its start (a reply that ran past the end of the context is caught too); text that is still too dense is read again in smaller pieces. Analysis calls start the local model with the same settings as questions, so Ollama doesn't load it again between an upload's analysis and a question. When the notes are too long for one local call, neighbouring notes are merged first; a merge whose reply can't be used leaves its notes as they were and merges fewer at a time. The upload list shows each step ("Analyzing section 3 of 12 with …", "(sampled from 61)" when sampling, "Combining the notes of 12 sections"), every call is in the usage log, and each section's notes are kept with the job, so a retry doesn't ask for them again. At most `ANALYZE_MAX_SECTIONS` (default 24) sections are read: a document needing more is sampled evenly from first to last section, and marked `partial: 24 of 61 sections, 39% of the text` (shown in its detail; "Not analyzed" on its card when nothing could be read). A section whose reply can't be used (not JSON, cut off, a refusal) is left out and counted the same way. File names are cut to 200 characters in the prompts. If the analysis fails, a new upload is still added and searchable, marked `none: <reason>`; a re-read, or an upload replacing its duplicates, fails instead, so no metadata is lost. Documents analyzed before this was added and marked just `partial` were analyzed from their start only; a re-read covers them whole |
| Key details | The analysis also reads, when the document states them, the date it bears (`document_date`) and, for receipts, bills and invoices, who issued it (`vendor`), the total (`total_amount`, `currency`) and, for bills and invoices, when payment is due (`due_date`). Dates are kept as `YYYY-MM-DD` and only when they are real dates (an ambiguous one such as 03/04/2026 is left out); an amount is kept when it is plain digits with a decimal point (a decimal comma when there is no point), and its currency only with it, as a three-letter code. Commas grouping thousands are dropped where they can't be decimals ("1,234.56", "12,000,000"); a lone comma before three digits ("1,234") could be either, so that amount is left out. A currency code written with the amount ("GBP 42.10", "42.10 GBP") is taken off it, and when the model gave no currency, that code, or a £ or € sign, gives it. In a document's detail, **Total** takes the same forms, and asks about "1,500" ("Is that 1500 or 1.50?") rather than guessing. Manuals and letters get none. The vendor is searchable with the keywords. The page shows them on cards and in the list's columns, sorts and filters by them, and edits them in a document's detail (Vendor, Total and Due date show for receipts, bills, invoices and statements, or once one has a value; **+ Add vendor, amount or due date** otherwise). The user can change any of them, the title and the type too (`PATCH /api/documents/<id>`, below); each field changed is listed in `user_edited`, and re-reading or replacing the document keeps it. Older documents have none. The rules for the date format and the folder are in the prompt as well as in the schema: Ollama turns a schema into a grammar without showing its descriptions to the model, and told only there, `qwen3.5:9b` wrote "3 November 2026" for a date and made up a new folder path beside an existing "Receipts" |
| Document types | The analysis is given the library's document types (most used first, one spelling of each, 40 at most, about 1,200 characters) and asked to copy one exactly when it fits, and otherwise to give a short general type of 1-3 words ("Receipt", "Service manual", "Wiring diagram"), never the document's own title. Whatever type a model gives (local or Claude, for an upload, a re-read or a **Replace**) is then tidied: spaces collapsed, quotes, bullets and punctuation around it dropped, 60 characters at most, in sentence case that keeps acronyms and words with capitals inside ("Technical Manual / Service Guide" becomes "Technical manual / service guide", "service manual" "Service manual"; "IRS form W-2" and "iPhone receipt" stay as they are, and "SERVICE MANUAL" becomes "Service manual"). A type the library already has under another spelling becomes the library's (its most used spelling): the same letters and digits ignoring case, spaces and punctuation ("W2 form", "W-2 form"), or the same words in any order, plurals aside ("service manual / technical guide" and "Technical Manual / Service Guide", "receipt" and "Receipts"). A re-read or a Replace leaves out the documents it describes anew, so a wrong type is neither shown to the model nor kept. A type typed in the page is the user's: it is kept as typed, apart from its spaces, and later analyses reuse its spelling. Types already in the library are not rewritten; documents analyzed before this keep theirs (the page shows every type with a capital and groups them ignoring case) |
| Folders | Documents can be kept in nested folders (a folder can hold folders), each document in one folder or in none (Unfiled). Names are trimmed, at most 100 characters, without `/` or control characters, and unique within their parent ignoring case (so "Straße" and "STRASSE" clash); a rename that only changes case is fine. A folder can't be moved into itself or one of its own folders, and folders go 20 levels deep at most (400 for a deeper folder, move or `path`: every listed folder carries its whole path). Deleting one moves its documents and folders to its parent (Unfiled and the top level for a top-level folder), renaming a folder whose name the parent has already "Name (2)", "Name (3)" and so on; or, with `contents=delete`, deletes it, every folder in it and every document in them, but only when `confirm_documents` is how many documents that is now (409 with the counts otherwise). Uploads on their way into a deleted folder go to its parent (or Unfiled), the one being read at that moment too, and are never auto-filed elsewhere; chats limited to it forget it. Folder ids are never given out again. In the page (see Documents view): **New folder** (top level, or inside one), **Rename…** (or F2), **Move to…** (or drag it onto another folder; a folder can't go into itself, and a name already used there is refused, never merged), and **Delete folder…**, which says what it holds and moves its contents up unless **Delete the folder and the N documents in it** is chosen and "I understand" ticked. The API: `GET /api/folders` (every folder, sorted by path: `id`, `name`, `parent_id`, `path` as a list of names, `doc_count`, `total_count` with its subfolders', `created_at`, `updated_at`); `POST /api/folders` with `{"name", "parent_id"}` (201; 409 `{"error", "conflict": {id, name}}` for a name in use); `PATCH /api/folders/<id>` with `{"name"}` and/or `{"parent_id"}` (null for the top level); `DELETE /api/folders/<id>?contents=move\|delete&confirm_documents=<n>` (`{deleted_folders, moved_documents, moved_folders, deleted_documents, renamed: [{id, from, to}], parent_id}`). Documents: `POST /api/documents/move` with `{"ids": [...], "folder_id": id or null}`, or `{"ids": [...], "path": "Household/Bills"}`, which makes the folders missing from the path (`{moved, folder_id, created, from: {id: its folder before}}`, what an Undo needs); `GET /api/documents?folder=<id>\|unfiled` (with `recursive=0` for its own documents only), also with `q` (and `limit`, 10 by default, 200 at most), and `GET /api/search?q=…&folder=…` (and `limit`, 1-50) |
| Auto-filing | The analysis is given the existing folders' paths (200 at most, about 6,000 characters) and suggests one, or a new category ("Receipts"), with its confidence. An upload made into Unfiled with `auto_file` on goes into the folder it suggests only when the model is sure (`high`), the path names an existing folder (ignoring case), and that folder is named for what the document is or is about: a word of its name (of its last level with letters, so "Receipts/2026" counts as Receipts) matches one of the document's type, title, vendor or keywords, plurals, endings and accents aside ("Bills" and "water bill", "Statements" and "Electric Service Statement"). Being sure isn't enough on its own: on staging, `qwen3.5:9b` was sure a home insurance policy belonged in Bills and barn notes in Tractor/Manuals; such a folder is only suggested. The prompt asks for the same (a folder that could merely hold the document doesn't fit). Folders are never made without a click. Otherwise the suggestion is kept on the document (`suggested_folder`, `suggestion_exists`) while it is Unfiled. An upload made into a folder stays there. Replacing a duplicate (**Replace**) keeps the folder of the copy it replaces, and a re-read never moves a document. `filed_by` is `auto` for a document auto-filing put in its folder, until it is moved. A finished upload job's `result` says where the document went: `folder_id`, `filed` (`auto`, `chosen`, `kept` or null), `suggested_folder`, `suggestion_exists` and `folder_note` (when its folder was deleted before it was saved). `PATCH /api/documents/<id>` with `{"suggestion": "apply"}` moves it to the suggested folder, making it if need be (`created` lists the folders made), and `"dismiss"` forgets the suggestion. In the page a suggestion shows as a chip on the card ("→ Receipts", or "→ new: Receipts" when there is no such folder yet: a click makes it and moves the document, with **Undo**), as a banner in the detail (the only place with **Dismiss**), and, in Library and Unfiled, grouped by folder ("Receipts · new folder · 3 documents" with **Create and move 3** and **Show**); the Unfiled row in the tree has a dot while any are waiting. Moving a document forgets its suggestion. On staging with `qwen3.5:9b`: a receipt photo went into "Receipts", a water bill into "Household/Bills", and a manual uploaded into "Tractor" stayed there with no vendor or total. With the name check, a home insurance policy and barn notes, for which it still chose Household/Bills and Tractor/Manuals, stayed in Unfiled with those as suggestions, while a receipt photo and an electric bill photo were still filed into Receipts and Household/Bills |
| Documents API | `GET /api/documents` lists every document as before, each with `folder_id`, `filed_by`, `suggested_folder`, `suggestion_exists`, the key details, `user_edited` (a list), `kind` (`pdf`, `image`, `markdown`, `docx` or `text`, from the extension) and `thumb` (its thumbnail's URL, or null). `GET /api/documents/<id>` adds `pages` (null without pages) and `copies` (`[{id, folder_id}]` of other documents holding the same file). `PATCH /api/documents/<id>` takes any of `title` (1-300 characters), `doc_type` (at most 60, kept as typed apart from its spaces: see Document types), `document_date` and `due_date` (`YYYY-MM-DD` or null), `vendor` (at most 200, "" for none), `total_amount` (a number or null), `currency` (three letters or null), `folder_id` (a move; null for Unfiled) and `suggestion`; a bad value is a 400 naming the field. `GET /api/documents/<id>/text?max=200000` gives a document's text for a preview: a Markdown or text file's kept original as written (`source: "file"`), anything else the text indexed for it (`"chunks"`), with `truncated`, `kind` and `bytes` |
| Photos | A photo of a receipt, bill or page is read by the vision model (`OLLAMA_VISION_MODEL`, sent at most 2,000 pixels on its longest side, turned upright by its EXIF) or, with a Claude model, by Claude from one image block (1,568 pixels at most); Auto reads it locally and switches to Claude only when Ollama fails, as for PDFs. Its text is then analyzed and indexed as any other; photos have no pages, so answers cite the file. One with no text fails with "No text found in the photo". The original is kept as the type of its bytes (a PNG named `.jpg` is a PNG), never what the browser said. A JPEG carrying more pictures after the first (MPO to Pillow: an iPhone's HDR gain map or depth map, and many Android and camera photos) is taken as the JPEG it is, and its first picture is read. On a phone, **+ Add › Take a photo** opens the camera; the detail shows the photo with "Text read from the photo" under it, to check the reading against it |
| Markdown | `.md` and `.markdown` files can be uploaded (picker and drag and drop) and are indexed as text. Opening the original shows it as plain text (`text/plain; charset=utf-8`), never as a web page, and `/text` gives it as written. A document's detail previews it **Formatted** (headings, lists and task lists, quotes, tables, code blocks, links) or as **Plain text**. The preview comes from a small renderer of the page's own (`app/static/md.js`), which builds elements one by one and never parses HTML: raw HTML and scripts in the file stay text, links open only `http(s)` and `mailto` addresses (in a new tab, with no referrer), and an image shows as a chip naming it and its site, never loaded. It reads at most 200,000 characters, and nesting deeper than 6 levels shows as text, so a hostile file can't stall the page (a 140 KB one with 500 nested quotes, a 2,000-row table and 100,000 asterisks renders in well under a second). A file starting with a byte order mark (as Windows PowerShell 5.1 and Visual Studio save UTF-8) is indexed and previewed without it, so its first heading is still a heading. Upload and preview only: no web page import, conversion or export |
| Thumbnails | The upload job makes a thumbnail of page 1 of a PDF or of a photo (WebP, 400 and 1,200 pixels wide, no metadata), kept in `THUMBS_DIR` by the original's hash, so copies share them; one that can't be made leaves the document with no thumbnail rather than failing it. Documents uploaded before this get theirs when first asked for, one at a time. `GET /api/documents/<id>/thumb?size=card\|large&v=<hash>` serves one: cached for good when `v` is the file's hash (as `thumb` gives it, since document ids are reused), revalidated by ETag otherwise; 404 for text, Word and Markdown files, documents with no kept original, and ones that can't be rendered. They are removed with their original, and not backed up (they can be made again). Cards and list rows show the small one (lazily), and a document's detail the large one; without one (older documents, text, Word and Markdown files, or one that fails to load) they show a page-like icon with the file's type |
| Metadata base | PostgreSQL tables `documents` (with its folder, key details and edited fields) and `chunks` (with each chunk's pages), `folders`, each with a generated `tsvector` column and a GIN index for full-text search (English stemming with no stop words, over the metadata with the vendor, and over the full text), `chunk_vectors` (one pgvector embedding per chunk, with the model that made it and its size, and an HNSW index per size), `conversations` (with the documents and folders their last question was limited to) and `messages` (saved chats), `jobs`, `usage`, `instructions` and `settings`. Ids are never given out again after a delete. Timestamps are text in UTC (`YYYY-MM-DD HH:MM:SS`) and JSON is text, as the API gives them out. Missing tables and indexes are made when the app starts, under an advisory lock |
| Originals | Every uploaded file is kept by `app/storage.py`: in `FILES_DIR` (default `/data/files`), an S3 bucket or an Azure Blob container (`STORAGE_BACKEND`), stored once per distinct content and named by its SHA-256. **Open** in a document's detail and its ⋯ menu shows it: PDFs open in the browser's viewer, plain text and Markdown as plain text, and JPG, PNG and WebP photos as images; other types download (HEIC too, which browsers can't show). Photos and text are served with `Content-Security-Policy: sandbox; default-src 'none'`, so nothing in them can run or load. `GET /api/documents/<id>/file` serves it. Deleting a document removes its file, and its thumbnails, once no other document uses it. Documents uploaded before originals were kept have no file and no Open link |
| Duplicates | Uploads are hashed (SHA-256). If the same file is already in the library, the upload stops before any model reads it, and its row in the upload queue asks: **Replace** (read the new upload, then delete the earlier copies), **Keep both**, or **Skip**. Through the API: the form field `on_duplicate` is `replace` or `keep`; without it the answer is 409 with the earlier copy's id, file name, date and model. A copy that is still queued or being read also counts (say the file was picked twice): the 409 then has `in_progress: true`, and only **Keep both** or **Skip** are offered. Documents uploaded before hashing never count as duplicates |
| Usage | Every model call (reading PDF pages, analyzing a document, each section of a long one included, embedding passages and questions for search by meaning, answering) is logged with its model, tokens and cost in the `usage` table as it happens, including calls made by uploads that then failed, Claude answers that ended in a refusal, and answers stopped or broken off part way (their output tokens estimated, see Streaming answers). Calls made by a job carry its `job_id` and are linked to the document when the job finishes (failed attempts before a successful retry too). Deleting a document keeps its rows but clears their `doc_id`. The **Usage** button shows totals per model and per day for the last 7, 30, 90 or 365 days; `GET /api/usage?days=30` returns the same. Claude costs come from the list prices in `PRICES` in `app/llm.py` and are estimates, not the invoice. Cache reads have their own price per model (5% of the input price on Opus and Sonnet 5.5, 2.5% on Fable 5.2, 10% on Haiku 5.5), and cache writes cost 1.25x the input price. Models missing from the table count as $0. Local models cost nothing. If the log can't be written (say the database is unreachable), the answer or upload still goes through and the error goes to the server log |
| Search | The search box in Documents matches documents at once in the page (title, file name, type, keywords, summary, vendor and folder name; every word, ignoring case and accents), then adds the server's matches by metadata, best first, folders whose name matches, and passages that contain the words, with highlighted snippets and, for PDFs, their page (**Open page 12**). In a folder it searches the folder and its subfolders, or **Everywhere**; results show their folder. It searches by keywords only, since it marks the words it found. Common words ("the", "will", "it") are left out when other words remain; typed alone they are searched for, so "will", "IT" or "WHO" still find a will, an IT policy or WHO guidelines. A snippet is plain text: the Markdown and HTML a model wrote when it read a page (headings, bold, table pipes and `\|---\|` rows, bullets, `<br>` and other tags, entities) is taken out, a table's cells are separated by " · ", and white space is collapsed. Through the API, both searches can be limited to a folder (see Folders). `GET /api/search?q=` gives each passage's `snippet_parts`, the snippet as a list alternating text and the words found, always starting and ending with text (perhaps ""), so the words found are at odd indexes, as JavaScript's `str.split(/(re)/)` gives them (`["… replace [see ", "figure", " 3] …"]`), and `snippet`, the same text with each word found in square brackets, for older clients (a passage's own brackets look the same there, so the page uses the parts). Snippets come from Postgres's `ts_headline` (one stretch of about 24 words round the words found), which marks the words found with two Unicode noncharacters (U+FDD0, U+FDD1); they are dropped from a document's text when it is indexed, so they can't be mistaken for its text |

## Keeping token use down

- **Retrieval instead of whole documents:** a chat turn sends only the top-K passages (`TOP_K`, default 5, about 1,500 characters each), not entire files. Search by meaning runs on the local embedding model, so it adds nothing to a Claude bill.
- **Prompt caching:** chat requests set `cache_control`, so the system prompt and the earlier conversation are read from cache (5% of the normal input price on Opus and Sonnet 5.5, 2.5% on Fable 5.2, 10% on Haiku 5.5). The server keeps each question exactly as it was sent and replays the earlier turns from the saved conversation, so the prefix stays byte-identical; streamed and whole answers send the same request, so they share the cache. Each answer shows how many tokens were read from and written to the cache. **Stop** ends an answer you don't need there (closing the page doesn't: the answer is written to the end).
- **Bounded analysis:** one analysis call sends at most `CLAUDE_ANALYZE_CHARS` (default 500,000) characters to Claude, or `OLLAMA_ANALYZE_CHARS` (default 40,000) to a local model, which has a much smaller context window (fewer for text dense in figures, as it is sized by its tokens). Longer documents are analyzed in sections of that size, so the analysis reads the whole text, up to `ANALYZE_MAX_SECTIONS` sections (default 24); past that it samples. The full text is always indexed and searchable either way. A 500,000-character section is roughly 125,000-170,000 input tokens, so analyzing a very long document costs noticeably more on Opus than on Haiku or Sonnet; the estimate counts every section, and lowering `ANALYZE_MAX_SECTIONS` caps what one document can cost.
- **PDF reading costs tokens:** each page Claude reads is billed as an image plus its text (roughly 1,500 to 3,000 input tokens), and the transcription is billed as output. By default Claude reads only scanned pages, so a PDF with a text layer costs just its metadata call. Leave **Claude reads every page** off unless the layout needs it, pick Claude Haiku 5.5 under "Read with" to make reading cheap, or use a local model to spend nothing. Jobs estimated at `CONFIRM_COST_USD` or more wait for a confirmation.
- **Low effort by default:** `CLAUDE_EFFORT=low`. Raise it if you want more careful answers.

## Backups

The `backup` service in `docker-compose.yml` (the same image, running `python -m app.backup`) backs up the library every night at `BACKUP_HOUR` into the `backups` volume:

- **The database:** a `pg_dump` of the library in its custom format. The dump and the count of documents logged with it come from one exported snapshot, so an upload or an answer being saved at that moment is either all in it or not at all. It is checked (`pg_restore --list` must read it, and it must hold table data), and only then named `metabase-YYYYMMDD-HHMM.dump`. The newest `BACKUP_KEEP` (14) are kept; older ones are deleted, and other files in the volume are left alone (snapshots from before Postgres, `metabase-*.db`, included).
- **The originals:** each original in the store (the local folder, the S3 bucket or the Azure container) that the backup doesn't have yet is copied to `files/` in the volume, and checked against the SHA-256 in its name. Copies are only ever added, so the original of a deleted document stays recoverable. The volume grows by every distinct file ever uploaded; delete old ones by hand if you need the room. With S3 or Azure, this puts a copy of the originals on this machine, out of the cloud account's reach.

The service only reads the library. The hour is the container's, which is UTC unless you set `TZ`: for 3 a.m. in New York, put `TZ=America/New_York` in `.env`. The service looks at the clock every minute and backs up when no snapshot has been taken since the last `BACKUP_HOUR`: a night the machine was off or asleep is made up soon after it is back, and the first snapshot is taken as soon as the service first starts. A failed backup is logged and tried again 30 minutes later. `docker compose logs backup` shows each one.

```bash
docker compose exec backup python -m app.backup --now    # take one now
docker compose exec backup python -m app.backup --list   # list the snapshots and originals
docker compose cp backup:/backups/. /mnt/d/chatbot-backups   # copy them out of Docker, to another disk
```

The `backups` volume is on the same disk as the library (inside WSL's virtual disk on Windows), so it guards against mistakes and a damaged database, not against losing the disk. Copy it somewhere else now and then: another disk (`/mnt/d/...` is the D: drive from WSL), or a USB drive. Not into the repo folder: the copy holds every document's text, the conversations and the original files, and a `git add` could take them to GitHub (`.gitignore` covers a `backups/` folder there, but no other name).

To restore a snapshot:

```bash
docker compose stop chatbot                                   # the app keeps some of the library's state in memory
docker compose run --rm restore                               # lists the snapshots
docker compose run --rm restore metabase-20261112-0300.dump   # or: latest
docker compose start chatbot
```

The `restore` service isn't started by `up`; `docker compose run` builds it from the current code and starts it on its own. It refuses while the app is running: the app holds a shared advisory lock in the database for as long as it runs, and waits for a restore under way to finish before it starts. It checks the snapshot, dumps the library it is about to replace into the backups volume as `before-restore-<time>.dump` (delete that once you're happy; restore it by renaming it `metabase-<date>-<time>.dump`), puts the snapshot back with `pg_restore --clean` in one transaction (a failure part way changes nothing), and copies back the originals the snapshot's documents use that the store lacks. Anything saved after the snapshot was taken (uploads, conversations, usage) is not in it. A snapshot from an older version of the app is brought up to date when the app starts. Thumbnails (`/data/thumbs`) are not backed up: they are made again from the originals when first asked for.

## Where originals are kept

`STORAGE_BACKEND` decides (`app/storage.py`):

- `local` (the default): files in `FILES_DIR`, `/data/files` in the `metabase` volume.
- `s3`: an S3 bucket, `S3_BUCKET`, or any S3-compatible store with `S3_ENDPOINT_URL`. Give the app `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` (in `.env`) for a user or role allowed `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` and `s3:ListBucket` on the bucket (or on `S3_PREFIX/*` in it).
- `azure`: an Azure Blob Storage container, `AZURE_STORAGE_CONTAINER`, with `AZURE_STORAGE_CONNECTION_STRING`, or `AZURE_STORAGE_ACCOUNT_URL` plus `AZURE_STORAGE_KEY` or a SAS token in `AZURE_STORAGE_SAS_TOKEN`.

`S3_PREFIX` / `AZURE_STORAGE_PREFIX` put the originals in a folder of the bucket or container, so it can hold other things. Objects are named by their SHA-256 and written once: storing the same file again does nothing, and an upload only shows under its name once it is complete. The app reads them back to open a file, make a thumbnail, preview text or re-read a document. **Open** is served by the app, not by a link to the bucket, so it keeps the sign-in and the same headers (the file is read into memory first, so very large files take a moment). Thumbnails stay a local cache in `/data/thumbs`.

```bash
docker compose exec chatbot python -m app.storage --check        # which store, and can it be written, read and deleted
docker compose exec chatbot python -m app.storage --copy-local   # after switching to s3 or azure: copy /data/files into it
```

Switching stores doesn't move anything by itself: run `--copy-local` once after switching from `local`, or documents uploaded before can't be opened or re-read (their text and search are in the database and keep working).

## Moving from SQLite

Before Postgres, the library was one SQLite file, `/data/metabase.db`, in the `metabase` volume. Move it over once, into the new, empty database:

```bash
docker compose up -d --build postgres chatbot
docker compose exec chatbot python -m app.migrate /data/metabase.db --dry-run   # what it would copy
docker compose exec chatbot python -m app.migrate /data/metabase.db
docker compose restart chatbot
```

Every row keeps its id (each table's ids carry on after the highest), so saved chats limited to documents or folders, open tabs and the usage log still point at the same rows. Vectors are copied as pgvector vectors, each size gets its HNSW index, and the full-text index is made from the text. Libraries made by any earlier version of the app can be moved: columns they lack are given their defaults. It runs in one transaction and refuses a database that already holds documents. The SQLite file is only read: keep it until you have checked the library, then delete it. The originals stay in `/data/files`; with `STORAGE_BACKEND=s3` or `azure`, run `python -m app.storage --copy-local` as well.

## Reach it from the LAN (Windows with WSL)

When Docker runs inside WSL, other machines reach the app through a Windows port proxy (`0.0.0.0:8000` to WSL's address, port 8000) and an inbound firewall rule, **Chatbot 8000**. WSL gets a new address when it restarts, which leaves the proxy pointing nowhere. WSL's mirrored networking would make the proxy unnecessary, but it needs Windows 11 22H2 or later, and this machine has 21H2 (build 22000). Instead, `scripts/portproxy.ps1`:

1. starts the WSL distro (`vostok`) if it isn't running, and keeps it running with a hidden `wsl.exe -d vostok --exec sleep infinity` (WSL stops a distro soon after its last window closes; Docker and the containers, all `restart: unless-stopped`, start with the distro);
2. reads the distro's address (`hostname -I`, the first one);
3. adds or updates the port proxy rule for `0.0.0.0:8000` if it points anywhere else;
4. makes sure the IP Helper service, which carries the port proxy, is running, and that the firewall rule exists (it adds one for TCP 8000 if there is none, and leaves a disabled one disabled).

Run again, it changes nothing. It logs what it did to `C:\ProgramData\Chatbot\portproxy.log`. A step that fails (IP Helper won't start, say, or the keepalive ends at once) is logged, the other steps still run, and the script ends with exit code 1, which the task shows as its last result. Other port proxy rules are left alone.

One-time setup, from an **elevated** PowerShell (Run as administrator) in the repo folder:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\install-portproxy-task.ps1
```

This copies `portproxy.ps1` to `C:\ProgramData\Chatbot`, a folder only administrators can change (the task runs the script with full rights; any user may create folders in `C:\ProgramData`, so if this one is there already, Administrators take it over and its permissions are reset, and the install stops if it can't make sure of that), and registers the scheduled task **Chatbot portproxy**. The task runs it as you, with highest privileges, at startup (30 seconds after boot, whether anyone is logged on or not, with no password stored) and at logon. The install then runs the task once and shows its log. Run the install again after changing `portproxy.ps1`.

- To see what it would do, without changing anything: `powershell -ExecutionPolicy Bypass -File .\scripts\portproxy.ps1 -DryRun` (or `-WhatIf`). This works without elevation; without elevation and without `-DryRun`, the script refuses to run. Reading WSL's address starts WSL if it isn't running, even in a dry run.
- `wsl --shutdown` gives WSL a new address: afterwards, run `Start-ScheduledTask -TaskName 'Chatbot portproxy'`, or log off and on again.
- If the log shows WSL failing to start in the startup run, Windows didn't let WSL start with nobody logged on: run the install again with `-Interactive`, which runs the task at logon only, in your session.
- Both scripts take `-Distro` and `-Port`; `install-portproxy-task.ps1 -WhatIf` shows the task it would register.
- To remove the task: `install-portproxy-task.ps1 -Remove`. It leaves the port proxy and firewall rules, and prints the `netsh` commands that remove them.

## Develop and test

The tests run in Docker, against a real Postgres with pgvector and Azurite (Azure Blob Storage's emulator); S3 is faked in the process (moto). Each test gets a schema of its own, dropped after it.

```bash
docker compose -f docker-compose.test.yml run --rm --build tests            # all of them
docker compose -f docker-compose.test.yml run --rm tests -k storage          # pytest arguments go after `tests`
docker compose -f docker-compose.test.yml down -v                            # remove the test database
```

GitHub Actions runs the same on every push and pull request (`.github/workflows/tests.yml`). The tests use fakes for Claude and Ollama, so they need no API key or GPU. Without Docker, run Postgres with pgvector yourself, `pip install -r requirements.txt -r requirements-test.txt`, and set `TEST_DATABASE_URL` (and `TEST_AZURITE`, a connection string, for the Azure tests; without it they are skipped). To run the app the same way: `DATABASE_URL=postgresql://… FILES_DIR=data/files THUMBS_DIR=data/thumbs flask --app app.main run --debug`.

## Not done yet

- Batch analysis for bulk uploads (the Message Batches API is 50% cheaper but asynchronous)
- Undo of a move puts documents back in their folders but not a filing suggestion they had: any move clears it, and nothing sets it back
- Uploads started from another tab, device or API client show in Documents only once this page is focused again (after 30 s away) or finishes a job of its own
- Markdown in answers is shown as written (`**bold**`, `- items`), not rendered. The prompt asks for plain text, so it shows only when a question asks for formatting or a model ignores that
- Saved conversations have no length limit: Claude is sent the whole history with every question (cached, but it grows), while the local model gets only the latest exchanges that fit (see Auto)
- Sign-in is over plain HTTP: passwords and session cookies cross the network unencrypted, so someone who can watch the LAN's traffic can take them. HTTPS (a reverse proxy in front) would close that. A copied cookie works until it expires: **Log out** only removes it from that browser, while setting a new password for the account (or deleting it) ends all of its sessions
- Backups stay on the machine they were made on (the `backups` volume), until you copy them elsewhere
- Until the first account is made, anyone who can reach the port can open the setup page, but making the account needs the setup code from the app's log. Every account can do everything, so give one only to people you would trust with the whole library
